## 1. 검수 범위와 방법

완료보고서와 제출된 AirSim 실측 JSON을 대조하고, 작업지시서 #09의 좌표계 수정·다중 기체 RTH 충돌 회피·중복 RTH 방지 요구사항에 대해 `server.py`와 `test_orca_rth.py`의 실제 제어 및 판정 경로를 검토하였다.

독립 실행 검증:

- `python test_orca_unit.py`: 통과 (6개 테스트)
- `python -m py_compile server.py orca.py test_orca_rth.py`: 통과

AirSim Blocks 비행은 이번 검수 시점에 재실행하지 않았으며, 제출된 원시 측정 리포트와 이를 생성하는 코드의 동작 경로를 교차 검토하였다.

## 2. 확인된 통과 사항

- RTH 홈을 각 기체의 고유 스폰 지점으로 정의하고, 월드 좌표 기준 홈을 사용하려는 설계는 작업지시서의 권장 해석과 일치한다.
- 제출된 `orca_rth_report.json`은 3,576개 샘플, 샘플링 오류 0건, 충돌 0회, 최소 이격 3.43m 및 브라보·찰리의 수평 홈 오차 0.04m·0.40m를 기록한다.
- 테스트는 샘플 수·오류·충돌·최소 이격·착륙 정확도를 성공 조건에 포함한다.

## 3. 승인 보류 사유

### P1 — “동시 RTH”가 실제로는 직렬 실행됨

`_do_rth()`는 RTH 전체 3개 레그와 착륙이 끝날 때까지 `control_lock`을 점유한다. 따라서 Bravo RTH가 실행 중이면 Charlie RTH 스레드는 같은 락 획득을 기다리며, 두 기체의 ORCA 제어 루프가 동시에 실행될 수 없다.

`test_orca_rth.py`는 Bravo 요청 후 0.5초 뒤 Charlie 요청을 보내지만, 이 테스트 경로에서는 두 RTH가 시간상 겹치는지를 검증하지 않는다. 제출된 “다중 기체 동시/교차 RTH 충돌 회피” 결과는 사실상 단일 기체 RTH 두 번의 연속 실행일 수 있으므로, 작업지시서 #09의 핵심 충돌 회피 요구사항을 입증하지 못한다.

### P1 — 동일 기체 RTH 중복 방지가 원자적이지 않음

`rth_in_progress`에 대한 포함 검사와 `add()`가 락 밖에서 분리되어 있어, 거의 동시에 들어온 동일 기체의 두 요청이 모두 “미진행”으로 판단할 수 있다. 그 경우 중복 RTH 루프가 순차적으로 실행될 여지가 있다.

## 4. 재검수 조건

1. 전역 `control_lock`은 각 RPC 명령 또는 짧은 제어 틱에만 점유하도록 조정하고, 서로 다른 기체의 RTH ORCA 루프가 실제로 동시 진행되게 한다. 기존 제어 클라이언트의 스레드 안전성이 보장되지 않으면 기체별 제어 클라이언트 또는 별도 안전한 명령 직렬화 방식을 사용한다.
2. `rth_in_progress`의 검사·등록을 하나의 동기화 구역에서 원자적으로 처리하고, 중복 요청에 대해 명확한 거절 또는 진행 중 응답을 반환한다.
3. 테스트에 각 RTH의 시작·종료 시각을 기록하고, 두 기체의 ORCA 제어 구간이 실제로 겹쳤음을 필수 성공 조건으로 추가한다.
4. 위 수정 뒤 교차 RTH 실환경 시험을 재실행하여 샘플 오류 0건, 충돌 0회, 최소 이격 3.0m 이상, 홈 오차 1.5m 이하를 다시 입증한다.

## 5. 결론

좌표계 수정과 단일 RTH의 홈 정합성 증거는 긍정적이다. 그러나 다중 기체 RTH 충돌 회피라는 이번 작업의 핵심 기능은 현재 제어 락 구조상 실제로 동시 실행되지 않아 검증되지 않았다.
