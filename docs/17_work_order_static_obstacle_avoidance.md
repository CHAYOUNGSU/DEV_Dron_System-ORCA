# 작업지시서 #17: 정적 장애물(건물/지형/구조물) 회피 적용

- 작성자: Claude (설계 / Plan 역할)
- 구현 담당: Antigravity
- 검수 담당: Codex (독립검수 / Review 역할)
- 선행 작업: `docs/01~16_*` (Following Mode, 편대 집결, RTH 전부 ORCA 적용 및 승인 완료)
- 대상 레포: `DEV_Dron_System-ORCA`

이 문서는 구현 담당자가 이전 문서를 전부 읽었다는 것을 전제하지
않습니다. 필요한 배경은 이 문서 안에 포함되어 있습니다. 다만
`orca.py`와 세 곳의 기존 ORCA 통합 지점(`following_worker()`,
`_do_formation_assemble()`, `_do_rth()`)은 이미 검수를 통과해 동작
중인 **참고 구현체**이므로, 이번 작업도 그 패턴을 최대한 그대로
재사용합니다. 새로운 알고리즘을 만드는 작업이 아니라, 기존 ORCA
루프에 "가만히 있는 이웃"을 하나 더 추가하는 작업입니다.

---

## 1. 배경 및 목적

Following Mode(#01~#04), 편대 집결(#05~#08), RTH(#09~#16)까지 세 가지
주요 다중 기체 이동 경로에 전부 ORCA 충돌 회피가 적용되고 실측
검증까지 끝났습니다. 그런데 이 세 기능 전부 **다른 드론끼리만
서로 피합니다.** 프로젝트 초기에 검토했던 원본 조사자료가 명시했던
"Case B: 정적 장애물과의 충돌"(나무, 건물, 지형)은 지금까지 전혀
다루지 않았습니다 (`docs/00_INDEX.md`의 "최초 조사자료 대비 미착수
항목" 참고).

지금까지 모든 실측 검증이 Blocks 맵에서만 이루어졌기 때문에 이 공백이
드러나지 않았을 뿐입니다. CityEnviron(빌딩), LandscapeMountains(지형),
AbandonedPark(놀이기구 구조물) 같은 맵에서 Following Mode/편대
집결/RTH를 실제로 쓰면, 다른 드론은 정교하게 피하면서 바로 앞의
건물이나 구조물에는 그대로 충돌할 수 있습니다.

이번 작업의 목표: **드론이 아닌 정적 물체도 ORCA 계산에 "회피 대상
이웃"으로 포함시켜서**, 세 기존 기능이 다른 드론뿐 아니라 주변 정적
구조물도 함께 피하도록 만드는 것입니다.

## 2. 현재 시스템 구조 및 확인된 사실

### 2.1 재사용할 참고 구현체

- **`orca.py`**: 수정 불필요. `compute_safe_velocity(agent_pos, agent_vel,
  preferred_vel, neighbors, agent_radius, time_horizon, max_speed,
  max_vz, time_step)`의 `neighbors` 인자는 이미 리스트의 각 원소가
  `{"pos": (x,y,z), "vel": (vx,vy,vz), "radius": float, "weight": float}`
  형태이기만 하면 그게 드론인지 아닌지 전혀 구분하지 않습니다.
  **정적 장애물은 그냥 `vel=(0,0,0)`, `weight=1.0`(비상호적 - Following
  Mode의 알파와 완전히 같은 취급)인 이웃일 뿐입니다.** 이미 검증된
  패턴을 그대로 재사용하면 됩니다.
- **세 곳의 기존 ORCA 통합 지점** (전부 매 틱마다 `neighbors` 리스트를
  새로 구성하는 동일한 구조):
  - `following_worker()` (`server.py` 약 740~822행) - 팔로워별로
    `neighbors`를 구성하는 지점은 786~800행.
  - `_do_formation_assemble()` (약 980~1060행) - 동일 구조.
  - `_do_rth()`의 `run_rth_orca_leg()` (약 1460~1545행) - 동일 구조.
  - 세 곳 모두 `for other_id in DRONES_CONFIG.keys(): ... neighbors.append({...})`
    형태로 되어 있습니다. 정적 장애물은 이 리스트에 **추가 원소로
    합류**시키면 됩니다 (드론 이웃을 만드는 로직과 분리된 별도 함수로
    만들어서, 세 곳에서 공통으로 호출하는 것을 권장합니다).
- **ORCA 상수** (`server.py` 상단, 그대로 재사용):
  `ORCA_TIME_HORIZON_SEC=2.0`, `ORCA_AGENT_RADIUS_M=1.6`,
  `ORCA_MAX_SPEED_MPS=3.0`, `ORCA_MAX_VZ_MPS=2.0`,
  `FOLLOW_TICK_INTERVAL_SEC=0.1`.
- **연결 수명 주기** (`airsim_worker()`, 약 486~546행): 시뮬레이터
  포트가 열리고 새 `client_telemetry`가 연결될 때마다(재연결 포함)
  `spawn_verified`, `cached_vehicles_list` 등이 초기화됩니다(526~535행).
  **새 맵으로 전환되거나 재연결될 때마다 다시 실행되는 지점이므로,
  정적 장애물 목록도 이 지점에서 함께 (재)구축하는 것이 자연스럽습니다**
  (아래 3.1절 참고).

### 2.2 확인된 제약: 센서 기반 감지는 이번 범위에서 제외

`C:\Users\CHA\Documents\AirSim\settings.json`을 확인한 결과, 현재
`{"SimMode": "Multirotor"}`만 있고 `Vehicles`/`Sensors` 설정이 전혀
없습니다. 즉 LiDAR나 거리 센서(`getLidarData`, `getDistanceSensorData`)는
**지금 4대 중 어느 드론에도 설정되어 있지 않습니다.** 이걸 쓰려면
머신 전역 설정 파일을 수정해야 하는데, 이는 이 레포 밖의 파일이고
다른 AirSim 프로젝트에도 영향을 줄 수 있어 이번 작업 범위에서
**제외**합니다.

대신 AirSim이 이미 제공하는 "신 시점(God's-eye-view)" 씬 쿼리 API를
씁니다 (설치된 `airsim` 클라이언트에서 확인된 실제 시그니처):

- `simListSceneObjects(name_regex='.*')` → 씬에 있는 모든 오브젝트
  이름의 리스트. 정규식으로 필터링 가능.
- `simGetObjectPose(object_name)` → 해당 오브젝트의 **월드 좌표계**
  `Pose` (docstring에 명시됨 - 이 프로젝트가 이미 쓰고 있는 "월드
  좌표"(스폰 오프셋 보정 좌표) 개념과 같은 프레임으로 보입니다.
  단, 알파의 spawn_offset이 (0,0,0)이라 두 프레임이 우연히 일치해
  보일 뿐일 가능성도 있으니, 작업계획서에 실제로 검증한 방법과
  결과를 남겨주세요).
- `simGetObjectScale(object_name)` → Unreal 액터의 스케일
  **배율**(Vector3r)이며, 물리적 크기(미터)를 직접 알려주지 **않습니다**.
  안전 반경 산정에 그대로 쓸 수 없습니다 (3.3절 참고).

## 3. 요구사항

### 3.1 정적 장애물 레지스트리: 연결(맵 전환)당 1회만 구축

매 ORCA 틱(0.1초)마다 `simListSceneObjects()`를 호출하면 안 됩니다 -
씬 오브젝트 수가 수백~수천 개일 수 있고, 이 프로젝트의 다른 모든
RPC 호출과 마찬가지로 `control_lock`/`client_telemetry`를 통해야 하므로
틱마다 부르면 다른 제어 명령과 경합하며 성능을 심각하게 떨어뜨립니다.

**대신 `airsim_worker()`가 새로 연결될 때(2.1절의 526~535행 부근,
`spawn_verified`가 처음 `True`가 되는 시점 - 즉 맵이 완전히 로드된
직후) 딱 한 번만** 씬을 조회해서 정적 장애물 후보 리스트를 캐시하고,
이후 틱들은 이 캐시를 읽기만 하세요. 시뮬레이터가 꺼졌다가 다른
맵으로 재연결되면(`is_switching_simulator`) 캐시도 함께 무효화하고
다시 구축해야 합니다 - `cached_vehicles_list`가 이미 이 수명 주기를
따르고 있으니 같은 패턴을 그대로 쓰면 됩니다.

### 3.2 핵심 설계 판단 지점 (열린 질문 - 구현자가 조사 후 결정)

`simListSceneObjects('.*')`는 조명, 하늘, 트리거 볼륨, 이펙트 파티클
같은 "물리적으로 충돌하지 않는" 오브젝트까지 전부 반환합니다. 이걸
전부 정적 장애물로 취급하면 (a) 리스트가 너무 커져서 매 틱 ORCA 계산
비용이 감당 안 되고, (b) 실제로 부딪힐 리 없는 물체 때문에 드론이
불필요하게 회피 기동을 하게 됩니다. 반대로 필터링을 너무 공격적으로
하면 진짜 건물/구조물을 놓칩니다.

**완벽한 일반해는 없다는 것을 전제로**, 다음을 실제로 조사하고 작업
계획서에 근거와 함께 남겨주세요:

1. Blocks 맵과 (검증에 쓸) 다른 맵 최소 1곳에서 `simListSceneObjects('.*')`
   결과를 실제로 덤프해서 눈으로 확인하세요. 이름 패턴(예: Unreal
   프로젝트에서 흔한 `SM_`, `Building`, `Wall`, `Landscape` 접두사/부분
   문자열과, 반대로 걸러내야 할 `Light`, `Sky`, `Trigger`, `Cine`,
   `Player`, `Particle` 같은 패턴)이 실제로 이 맵들에서 어떻게
   나타나는지 확인 후 필터 전략을 정하세요.
2. 필터를 통과한 오브젝트라도, **드론 편대가 실제로 활동하는 영역
   (스폰 지점들 근처, 대략 반경 몇십 미터)에서 먼 것들은 애초에
   후보에서 제외**하는 것을 권장합니다 (연결 시점에 `simGetObjectPose()`로
   위치를 조회한 뒤 필터링 - 이러면 리스트가 훨씬 작아집니다).
3. 그래도 후보가 많이 남을 경우, **매 틱 ORCA에 넘기는 개수를
   제한**하세요 (예: 에이전트 위치 기준 가장 가까운 N개만, 또는 일정
   반경 이내만) - 드론 이웃은 최대 3개뿐이라 문제없었지만, 정적
   장애물은 훨씬 많을 수 있으므로 틱마다 거리순 정렬/컷오프 같은
   가벼운 사전 필터링이 필요합니다.
4. 최종적으로 어떤 필터 규칙을 썼는지, 왜 그렇게 판단했는지, 그리고
   이 필터가 놓칠 수 있는 사각지대(예: 이름 패턴에 안 걸리는 장애물)를
   작업계획서와 완료보고서에 솔직하게 기록하세요 - "이 맵에서는
   이렇게 확인했다"는 근거 있는 실용적 선택이면 충분하고, 모든 UE
   씬에 대해 완벽히 일반적인 필터를 요구하는 것은 아닙니다.

### 3.3 안전 반경 설정 (열린 질문)

`simGetObjectScale()`은 액터 스케일 배율이지 미터 단위 물리 크기가
아니므로, 오브젝트별 정확한 충돌 반경을 신뢰성 있게 계산할 근거가
없습니다. **오브젝트별 정밀 크기 추정을 시도하지 말고, 보수적인
고정 기본 반경**을 쓰는 것을 권장합니다 (예: 기존
`ORCA_AGENT_RADIUS_M=1.6m`보다 유의미하게 큰 값 - 건물/구조물은 보통
드론보다 훨씬 크므로). 구체적인 값과 근거(몇 개 샘플 오브젝트에 대해
실제 맵에서 눈대중/AirSim 뷰포트로 크기를 가늠해본 결과 등)는
작업계획서에 남겨주세요. 새 상수(예: `ORCA_STATIC_OBSTACLE_RADIUS_M`)로
별도 관리하세요 - 기존 `ORCA_AGENT_RADIUS_M`과 값을 공유할 필요
없습니다.

### 3.4 세 곳의 기존 ORCA 통합 지점에 전부 적용

Following Mode, 편대 집결, RTH **세 기능 모두** 정적 장애물의 위협을
동일하게 받습니다 (셋 다 임의의 맵에서 임의의 경로로 비행하므로).
2.1절에서 언급한 대로, 정적 장애물 이웃을 만드는 로직을 공용 함수로
뽑아서(예: `get_static_obstacle_neighbors(agent_pos) -> list`) 세 곳
전부에서 기존 드론 `neighbors` 리스트에 이어 붙이세요
(`neighbors.extend(...)` 또는 동등한 방식). `weight=1.0`(비상호적 -
장애물은 절대 스스로 피해주지 않으므로 에이전트가 회피 부담을 전부
져야 함), `vel=(0.0, 0.0, 0.0)`으로 고정하세요.

## 4. 비기능 요구사항

- **성능**: 매 틱 ORCA 계산에 추가되는 정적 장애물 수가 늘어나도
  `FOLLOW_TICK_INTERVAL_SEC=0.1초` 주기를 심각하게 벗어나면 안 됩니다
  (3.2절의 근접 필터/개수 제한으로 확보). 씬 조회(`simListSceneObjects`,
  `simGetObjectPose` 반복 호출) 자체는 연결 시 1회만 실행되므로 이
  요구사항은 주로 매 틱 실행되는 필터링/거리 계산 쪽에 해당합니다.
- **재연결/맵 전환 시 캐시 갱신**: 새 맵으로 바뀌면 이전 맵의 정적
  장애물 캐시를 그대로 쓰면 안 됩니다(잘못된 좌표의 "유령 장애물"이
  남음) - `is_switching_simulator`/재연결 수명 주기에 맞춰 캐시를
  버리고 새로 구축하세요.
- **교훈 A/B 재확인**: 이번 작업은 새로운 제어 명령 경로를 추가하지
  않고(기존 `moveByVelocityAsync` 호출 앞의 ORCA 계산에만 입력을
  추가) 새로운 AirSim 클라이언트도 만들지 않으므로, 이 프로젝트에서
  반복됐던 두 버그 유형(`enableApiControl` 재호출로 인한 추락,
  동일 기체에 대한 이중 제어 경로)이 재발할 가능성은 낮습니다. 다만
  씬 오브젝트 조회(`simListSceneObjects`/`simGetObjectPose`) RPC 호출도
  반드시 `get_control_client()` + `control_lock`(또는 읽기 전용
  `client_telemetry`, 어느 쪽이 적합한지는 `airsim_worker()`의 기존
  구조를 따르세요)을 통해서만 수행하고, 별도의 독립 AirSim 클라이언트를
  새로 만들지 마세요.
- 기존 세 기능(Following Mode, 편대 집결, RTH)과 회귀 테스트에 영향이
  없어야 합니다 - 특히 **Blocks 맵에서 정적 장애물이 오탐(false
  positive)으로 불필요한 회피 기동을 유발해서 기존 목표 도달
  정확도/시간이 눈에 띄게 나빠지면 안 됩니다.**

## 5. 작업 범위 및 제외 사항

- **포함**: 연결 시 1회 정적 장애물 레지스트리 구축, 필터링 전략 설계
  및 근거 문서화, 세 기존 ORCA 통합 지점에 정적 장애물 이웃 추가,
  맵 전환 시 캐시 무효화.
- **제외**: 센서 기반(LiDAR/거리 센서) 감지(2.2절 - settings.json
  수정 필요, 이번 범위 아님), 동적/이동하는 장애물, `orca.py` 솔버
  자체 수정(정적 장애물은 기존 이웃 포맷을 그대로 쓰므로 불필요),
  레이캐스트 기반(`simTestLineOfSightToPoint`/`BetweenPoints`) 접근
  방식 - 검토는 했으나, ORCA는 각 이웃의 "위치"가 있어야 회피
  반평면을 계산할 수 있는데 단순 가시선 판정은 이진값(막힘/안막힘)만
  주고 장애물의 위치 자체를 주지 않아 이번 god's-eye-view 레지스트리
  방식보다 통합이 복잡합니다 - 이번 범위에서는 채택하지 않습니다.
